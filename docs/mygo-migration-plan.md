# PicPiper：Go + MyGo 重做与框架评估

更新日期：2026-11-11。参考代码基线：`abd2961`。用户已确认继续使用 `migration/mygo`；分支无上游，与本地 `main` 和已记录的 `origin/main` 相同，未执行 fetch。

## 1. 目标与判断标准

用户明确愿意推倒重做现有实现，现有图片处理的质量也不足以成为新版本的验收标准。主要动机是 Rust 构建产生数 GB 文件、现有 app 体积超出预期，以及希望借真实项目探索和评估 Go GUI 框架。

因此，本项目以 Go + MyGo 的实际开发、构建和交付体验为中心。旧代码提供产品需求和部分经验；旧 DTO、15 个操作、队列实现、编码器输出、四格式全覆盖和六平台发布均不作为第一阶段必须复刻的条件。

优先回答：

1. 一个有实际用途的 MyGo 应用，安装体积能否保持在两位数 MB 的目标范围？
2. 开发构建、发布构建、增量修改的耗时与磁盘占用如何？
3. 原生窗口、文件选择/拖放、Go-JS 调用、调试和打包是否适合持续开发？
4. 增加图片处理和 S3 后，体积、依赖和维护复杂度如何变化？

“两位数 MB”是待实测目标，暂不假定官方框架示例的大小就是 PicPiper 成品大小。首轮以本机 macOS arm64 为验证目标，后续逐步扩展 Windows/Linux 和其他架构；首轮范围不等于最终平台承诺。

以下阶段划分保留最初的评估方案。现已完成 Go/MyGo MVP、S3 链路及现代图片格式支持；当前行为与实测数据以 [MVP 报告](mygo-mvp-results.md) 和 [编码器报告](mygo-codec-results.md) 为准。

## 2. 已核对的框架依据

[框架研究及一手来源](mygo-framework-research.md) 核对了 MyGo `v0.9.0`：

- 框架默认 `CGO_ENABLED=0`，本身不要求 Rust；最低 Go 版本 `1.27.3`，本机已满足。
- 支持 Vite 开发与前端资源嵌入、生成 Go-JS 类型绑定、原生对话框、路径形式的文件拖放、剪贴板、外链打开和窗口能力。
- 官方文档覆盖 macOS/Windows/Linux 的 arm64 与 amd64。Windows 需要 WebView2，Linux 需要 GTK/WebKitGTK；不随应用捆绑系统 WebView 有助于减小包体，但这些仍是运行条件。
- 具体交互和成品体积尚无本项目实测结果。native modules 被官方标为实验功能，首轮不依赖它。

Go 语言、无 cgo 与小体积之间没有自动等号。图片库、资源、CPU 架构、符号信息、签名和分发方式都会改变结果；Go 的 module/build cache 也可能达到 GB 级，是否改善用户的实际体验要实测。

## 3. 体积与构建成本的测量方法

### 分开记录不同口径

| 指标 | 记录方式与含义 |
| --- | --- |
| 可执行文件 | 字节数和构建参数，记录优化及符号裁剪策略 |
| 安装后的应用 | 整个 `.app` 的逻辑字节数与实际磁盘占用，包含资源、随附动态库和外部工具 |
| 下载包 | ZIP/DMG 等实际分发文件大小，不能代替安装体积 |
| 构建目录 | 本项目生成的可执行文件、中间文件、打包临时文件及重复构建后的增长 |
| 开发缓存 | Go build cache、module cache、前端依赖和工具缓存，区分项目独有与跨项目共享 |
| 外部运行依赖 | 系统 WebView 与用户额外安装的库/工具分别列出；不能通过把依赖放到包外来掩盖交付成本 |
| 构建耗时 | 依赖准备、首次编译、相同输入重建、单处 Go 修改、单处前端修改分别测量 |
| 运行表现 | 冷启动、空闲内存、批量处理峰值内存和交互响应 |

统一记录操作系统、架构、Go/MyGo 版本、构建命令、网络/依赖缓存状态。使用相同单架构 release 配置比较；universal 包和 debug 包另列。系统工具显示的 MiB、MB 与磁盘块占用需说明口径。

不为测量删除用户的全局 Go 或 Rust 缓存。后续若测冷缓存，在独立目录设置本次测量的 `GOCACHE`/`GOMODCACHE`；缓存目录、依赖下载时间与编译时间分别报告。

### 用功能增量定位体积来源

每个节点都保留构建参数、可运行产物和上述指标：

| 节点 | 加入的内容 | 回答的问题 |
| --- | --- | --- |
| A | 最小 MyGo 窗口与简单前端 | 框架与基础打包的成本 |
| B | PicPiper 实际界面、文件选择/拖放、Go 调用 | 真实桌面交互的成本 |
| C | JPEG/PNG 检查、预览、重新编码与导出 | 轻量图片处理的成本与效果 |
| D | 候选 WebP 编码器 | 是否值得接受它带来的体积、构建与分发负担 |
| E | S3 上传、列举与必要配置 | 网络业务和 SDK 带来的增量 |
| F | 按需要加入 AVIF、更完整图库及其他平台 | 扩展能力是否仍满足目标 |

如果某节点体积显著增长，先查二进制、资源和随附库的组成，再决定精简或换方案。不会为了凑数字去掉正常使用必需的依赖，也不默认采用可执行文件压缩器。

### 目前能确认的仓库基线

2026-11-11 只读检查：`src-tauri/target` 不存在，因此无法从当前工作区测量旧 Rust 构建目录或旧 `.app`，也不为复现旧构建而安装 rustc。

当前 `du -sh` 显示：`dist` 432K、`node_modules` 252M、仓库 `.pnpm-store` 8.0K。这些是前端目录的磁盘占用，既不是旧 app 大小，也不是 MyGo 的测量结果。用户反馈的数 GB Rust 构建占用作为问题背景保留。

若已有旧 release 产物可获得，可直接测量其安装体积；否则旧版本该项标为未测，不虚构对比数字。

## 4. 重做范围与技术取舍

### UI 与 Go 服务

首轮建议复用现有 React/Vite 和有价值的视觉组件，减少同时变化的因素；页面、状态管理和队列可随新流程重写。后端使用新的 Go 服务和 MyGo 生成绑定，不先构建一套兼容全部 Tauri 命令的适配工程。

第一轮只建立当前功能需要的模块：桌面启动、图片处理、任务/文件管理。加入 S3 时再增加存储和配置模块。避免在验证框架之前预建大量接口与分层。

图片与网络逻辑尽量不依赖 MyGo，使其可以独立测试；桌面层只组合窗口、绑定和系统能力。Go-JS 错误按新领域需要设计，前端能够区分失败原因即可；沿用旧调用方时再适配其业务错误码。

### 图片处理重新选型

- 用 Go 标准 JPEG/PNG 实现建立最小可用链路，显式处理 EXIF 方向和透明度策略；此步骤用于建立功能与体积基线，不代表最终默认格式已经确定。
- WebP 优先做候选评估；旧版本默认 WebP 可作为需求参考，但不要求相同编码器或相同质量数值。
- AVIF 后置，按画质/体积收益、编码耗时和工具链负担决定是否加入。缺少 AVIF 不阻塞第一轮 MyGo 评估。
- 比较纯 Go、cgo/原生库或随附工具时，把全部依赖和体积计入结果。尽量维持无需本机 rustc 的开发链；引入任何编码器前先核对底层依赖，避免间接依赖 Rust 编译。
- 预览传输可重新设计。大图优先验证受控图像协议/文件资源，避免不必要的完整 base64 往返；不能假设系统 WebView 原生支持所有输入格式。

质量基准使用固定样本集：照片、截图/文字、透明图、EXIF 旋转图、大图和损坏文件。评价方向/尺寸正确性、透明度、可见失真、输出体积、元数据、耗时与内存；旧版输出只作参考。同名 quality 数字不能当作跨编码器质量等价。

### 仍需保留的产品底线

重做允许改变实现和功能排序，但输出不能覆盖原图或用户其他文件；任务失败需能理解，后台任务需有限流，过期结果不能污染新操作。密钥不进入日志或前端资源，S3 上传是否覆盖需有明确策略。

新版本验证阶段使用独立数据目录，避免原型运行或 `mygo generate` 的初始化触碰旧配置。保留旧文件；以后若需要旧配置导入，再实现明确的读取/复制流程，不把原路径和 JSON 格式当作新架构的前提。

旧数据定位依据保留：[Tauri 2.11.3 的 app_data_dir 源码](https://docs.rs/tauri/2.11.3/src/tauri/path/desktop.rs.html) 使用 [dirs 6.0.0 data_dir](https://docs.rs/dirs/6.0.0/dirs/fn.data_dir.html) 加上 `xyz.frankwei.pic-piper`；macOS 是 `~/Library/Application Support`，Linux 是 XDG data 目录，Windows 是 RoamingAppData。

## 5. 推进顺序与评估产物

### 第一轮：最小可运行应用与构建报告

固定兼容的 Go/MyGo/runtime 版本，在 macOS arm64 产出节点 A–C：

1. 完成窗口、Vite 开发体验和生产资源嵌入，尽早生成真正的 `.app`。
2. 实测 Go-JS 成功/失败调用、调试、文件选择/拖放和窗口行为。
3. 完成选图 → 检查/预览 → JPEG/PNG 处理 → 导出的最小闭环。
4. 对每个节点记录体积、冷/热构建耗时、缓存占用及运行表现，确认打包产物脱离开发服务器仍可用。

产物是可运行应用与测量记录，不要求先完成旧版 15 个操作、四格式或六平台发布。第一轮即使发现 MyGo 不适合，也应留下能解释原因的数据。

### 第二轮：有实际用途的图片工具

基于样本集评估 WebP 候选，改进图片处理体验；按需要加入批量队列、比较和导出。每加入一个重依赖就重测体积和构建成本，避免最后才发现偏离初衷。

### 第三轮：S3 与分发验证

增加实际需要的 S3/R2 功能与配置，再做 Windows/Linux 的构建和运行探索。SDK 选型可参考 [AWS Go endpoint 文档](https://docs.aws.amazon.com/sdk-for-go/v2/developer-guide/configure-endpoints.html)、[PutObject 条件写入](https://github.com/aws/aws-sdk-go-v2/blob/main/service/s3/api_op_PutObject.go) 与 [Cloudflare 官方 R2 Go 示例](https://developers.cloudflare.com/r2/examples/aws/aws-sdk-go/)；不预先为旧版全部功能建立兼容层。

验证签名、系统运行依赖、原生库分发和安装体验，再决定最终平台与格式范围。旧 Rust 源码可暂留参考；新 Go 构建不调用旧后端，收尾时再清理旧框架目录、npm 依赖、发布测试和 CI。

## 6. 验证与当前进度

上一轮已完成旧前端基线验证：13 个测试文件、125 项测试通过，`pnpm build` 通过。它们只能说明旧前端状态正常，不是重做版本的验收条件。测试随新行为调整，有价值的非覆盖、方向、任务并发等案例可以复用。

以上为最初规划时的状态。之后已完成原生应用重建、S3 链路和 WebP/AVIF/JPEG XL 读写、HEIC 读取；构建与真实应用验证见开头链接的实测报告。全程未安装或执行 Rust 工具链。

后续每阶段执行与实际功能相符的 Go/前端检查和桌面实测。最终框架评估应清楚记录：适用场景、开发体验、体积与构建成本、已遇到的问题、依赖负担以及继续采用或停止探索的理由。两位数 MB 若未达成，先报告分项数据与原因，再判断方案价值。
